01 / Project & delivery

From content to a live site.

Application
Astro + TypeScript + CSS

Static pages generated at build time, with small browser scripts for interactions.

Content
Markdown content collections

Only reviewed public copies enter the site. The private Obsidian vault stays outside the build.

Version control
Git + GitHub

Focused commits track each change. Initial work used main; this portfolio is isolated on a feature branch.

CI/CD
GitHub Actions

Updates to main, or manual dispatch, run build, tests, and type checks before uploading dist. The deployment token stays in GitHub Secrets.

Deployment workflow
Infrastructure
Azure Static Web Apps Free + Bicep

Bicep provisions hosting and optional custom-domain binding; the application workflow deploys files separately. Azure serves the site over HTTPS. The original Linux VM + Nginx template is retained.

02 / Key decisions

What I chose, and why.

01Keep the MVP small and static.

My choice
Start with an English profile, then add selected articles. No accounts or database.
Why
The job is publishing content, not managing user data. Copilot proposed Astro to support that scope.
Tradeoff
Content changes need a rebuild; private saved features would need more architecture.
Scope decision

02Publish reviewed copies, not the vault.

My choice
Manually select and review articles before copying them into the public site.
Why
Share useful knowledge without exposing unrelated private or internal notes.
Tradeoff
Some duplication and content drift, acceptable for two articles.
Publication policy

03Move from a VM to managed hosting.

My choice
After initially requesting a Linux VM, approve Copilot's Static Web Apps proposal when I asked for HTTPS and its cost.
Why
A static site does not need my own OS and Nginx to maintain. Managed HTTPS and the Free tier fit a low-spend MVP.
Tradeoff
Less server control and platform limits. Domain renewal is separate; Free hosting is not a measured total bill.
Hosting change

03 / What's next

Risks and improvements.

Planned work, not implemented features.

Bad releases
Add pull-request checks, post-deployment route checks, and rehearse restoring a known-good revision.
DNS, TLS or hosting failure
Add a lightweight availability check. Agree recovery targets before others depend on the site.
More articles
Introduce a selective publishing helper when manual copying becomes a burden; keep human review for privacy and content drift.
More traffic or features
Review actual costs and service limits before upgrading. Add an API or database only when a feature needs private state.

First priority: validate a release and its recovery path. Recovery has not been rehearsed; an uptime target is not yet set.
