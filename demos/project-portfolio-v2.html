01 / Brief & ownership

What I was solving.

A public professional profile with selected technical writing. The goal was to publish useful content, not build a multi-user application.

Original scope
English profile, experience, contact, and later two approved knowledge articles.
Budget now
$0-20 per month. Spend as little as practical for an owner-only static MVP.
Still undefined
Maintenance-hours budget, uptime target, and acceptable recovery time.

Budget and current audience were clarified on September 13, 2026, during this review. They are not presented as quantified requirements recorded before the original build.

My decisions: keep the MVP small and English-only; require reviewed public copies; request the initial VM; approve the managed-hosting change; require tests, focused commits, and no credentials in Git.

Copilot's contribution

Proposed Astro and managed hosting, and assisted with code, tests, Bicep, and deployment. This was not an independently hand-coded implementation.

A specific scope correction

I removed the early portfolio proposal because there were no substantial projects to show, and limited the site to English. The MVP design records that narrower scope.

This demonstrates product direction and review, not independently finding a generated-code defect.

Decision 01 / Product

Keep the application static.

I reduced the MVP to a useful profile. Copilot selected Astro for content-first pages; I continued with that approach as approved Markdown articles were added.

Requirement
Publish English content without accounts or per-user state.
Consequence
Generate pages at build time; omit the application server and database.
Tradeoff
Content updates require a build. Private persistent features would need additional architecture.
Reconsider if
A real feature needs private saved state or request-time behavior. A browser-only tool need not force a rewrite.
Evidence

The scoped MVP later gained two static article routes. This proves implementation scope, not an Astro performance advantage. Article implementation

Was Astro the only reasonable choice? Retrospective

No. Another static generator, such as Eleventy, is a credible alternative. Astro already provides the project's typed content and a path to isolated interactive components; no measured deficit has justified switching.

There was no head-to-head benchmark or weighted selection study. Astro fits; this record does not prove it objectively wins. A future comparison should use the same content to evaluate publishing effort, build cost, and delivered JavaScript.

Decision 02 / Content

Keep the private vault outside the build.

I required selection and risk review before publication, with no changes to the Obsidian source and no synchronization script at this stage.

Requirement
Publish selected knowledge without copying unrelated private material.
Consequence
Only approved public adaptations enter the site's content collection.
Tradeoff
Manual duplication and possible drift between private and public versions.
Reconsider if
Repeated copying becomes a demonstrated burden. Evaluate a selective, review-gated publisher, not whole-vault synchronization.
Evidence

The policy was committed before the articles. It records a control, not proof that every future edit is safe. Publication boundary

Why not a selective publishing script now? Retrospective

An allowlisted exporter could reduce duplication without exposing the entire vault. For two articles, I chose manual approval rather than creating and maintaining that tool.

A human can still miss sensitive content. Review must cover credentials, private identifiers, internal material, and copyright. Automation would not remove that responsibility.

Decision 03 / Hosting

HTTPS changed the hosting decision.

I initially requested the lowest viable Linux VM and a public endpoint. Later I asked for HTTPS and its cost. Copilot proposed Static Web Apps Free; I approved the migration and requested a separate reusable Bicep template.

Requirement
Public HTTPS with minimal spend and no application backend.
Consequence
Use managed static hosting instead of adding TLS operation to the HTTP-only VM baseline.
Tradeoff
Less server control and platform limits. Azure was the chosen environment, not a proven exclusive business requirement.
Reconsider if
Usage, server requirements, or reliability expectations exceed the service's capabilities or acceptable cost.

The selected tier has no base hosting charge under its Free-plan terms. Domain renewal is separate. No exact savings, operating-hours reduction, or total monthly bill has been measured here.

Why not GitHub Pages or another static host? Retrospective

They remain credible alternatives. The actual path evolved from my Azure VM request; I also explicitly wanted reusable infrastructure that others could deploy in their own environment.

This was not a scored multi-provider evaluation. Without an Azure requirement, compare static hosts on total cost, deployment effort, domain support, and required service guarantees. Familiarity alone does not establish a technical winner.

03 / Runtime & delivery

Two paths. Different failure modes.

Build passes, custom domain fails: where would I look? Not exercised
  1. Classify the failure: DNS, TLS, HTTP status, or incomplete rendering.
  2. Compare the custom domain with the generated Azure hostname. A working generated hostname narrows the issue toward the custom-domain path, but does not prove a DNS-only cause.
  3. Check CNAME resolution, domain binding, and certificate state; then compare the failing route with the deployed artifact and release history.
  4. If HTML works but visuals fail, inspect font/image requests. If both hostnames fail, investigate hosting state and published content as well as the client network.

This is a diagnostic plan, not a claim that an outage was reproduced or resolved.

05 / Risks & next proof

What remains unresolved.

Static does not mean failure-free.

The owner-only MVP prioritizes low cost over additional availability investment. Bad releases, DNS or certificate issues, and hosting failures remain possible. A numerical downtime tolerance and recovery objective are not yet agreed.

The next useful proof is recovery.

A proposed exercise would restore a known-good revision, validate its routes and assets, and record the recovery time and manual steps. It has not been run. Git history alone is not a tested recovery mechanism.

What would trigger more investment? Proposed
  • External users depend on the site: agree availability and recovery targets, then choose checks and hosting guarantees to match.
  • Usage or spend approaches the budget: inspect the actual bill and service limits before changing tiers or providers.
  • Publishing becomes frequent: add PR validation and test a selective publication helper against the review boundary.
  • A feature needs private state: define security and data requirements before adding an API or database.

This project demonstrates small-system delivery and scope decisions. It does not demonstrate enterprise scale, multi-team negotiation, or production incident management.

The VM answered my first request. Reconsidering it when HTTPS changed the requirements was the more important architecture decision.
