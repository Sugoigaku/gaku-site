01 / Discover

Define the need.
Then narrow the scope.

The starting point was not a technology stack. It was a visitor's three questions: who am I, what do I work on, and how can we connect?

Audience
Engineering peers, recruiters, and people arriving from GitHub or technical discussions.
Product goal
A credible professional presence, with room for a curated public knowledge library.
Constraints
English only, low running cost, mobile readability, minimal maintenance, and no private information in public content.
Acceptance
A complete profile, working contact paths, readable layouts, published routes, and passing build and content checks.

Build now

  • Introduction, experience, and contact
  • Responsive and accessible navigation
  • Approved English knowledge articles
  • Public HTTPS hosting

Wait for a real need

  • Accounts, comments, and a database
  • Search across a small content library
  • Automatic Obsidian synchronization
  • A portfolio before there were projects

Decision 01 / Scope

A complete small product beats empty sections.

Need
Launch something useful without creating unnecessary maintenance.
Options
A multi-page platform, or a single professional profile with room to grow.
Decision
Start with the profile. Add knowledge publishing when actual articles were ready.
Tradeoff
Fewer features at launch, but each one serves a concrete purpose.
Evidence
Initial MVP design

02 / Decide

Choose for the workload,
not the technology list.

The content changes when I publish, not on every visitor request. Static generation removes a runtime dependency without taking away the features the site needs.

Decision 02 / Publication boundary

The private vault is not a build input.

Need
Share selected technical knowledge without exposing private notes.
Options
Publish directly from Obsidian, or maintain reviewed public copies.
Decision
Select a note, review publication risks, approve the adaptation, then add it to the site.
Tradeoff
Manual copying is acceptable at this scale. Automation can wait until it becomes a real bottleneck.
Evidence
Publication review policy

Review covers credentials, customer details, internal links, resource identifiers, copyright, and personal financial data. The original Obsidian notes remain unchanged.

04 / Deliver

A working VM.
A better-fitting managed service.

The first deployment proved the site could run on a small Linux VM. The request for HTTPS prompted a second question: did this static workload need a server I had to maintain?

Initial deployment / Retained as IaC

Linux VM + Nginx

Compute + disk + IP

Full infrastructure control and a useful IaaS implementation. But the operator owns patching, Nginx, TLS setup, availability, and monitoring.

  • VNet, subnet, NSG, NIC, and public IP
  • Ubuntu and cloud-init build
  • HTTP-only reference baseline
Current production architecture

Azure Static Web Apps

$0 base hosting / month

Static output with managed HTTPS. A better match for a small public site without an application backend.

  • Free tier; usage limits apply
  • Custom domain with managed TLS
  • No OS or Nginx maintenance

Decision 03 / Total cost

Optimize ownership, not just the VM size.

Need
Serve public content over HTTPS at low cost.
Options
Add TLS and operations to the VM, or move the static build to managed hosting.
Decision
Move production to Static Web Apps; retain both reusable Bicep deployment options.
Tradeoff
Accept hosting limits and less server control. Domain renewal remains a separate expense.
Evidence
Both infrastructure implementations

Delivery, from branch to production

Separate the responsibilities

Bicep provisions the hosting resource. The application workflow uploads the built site. Infrastructure is not redeployed on every content edit.

Keep deployment secrets out of Git

The token is read from GitHub Actions secrets at runtime. The workflow uses read-only repository permissions and cancels superseded runs.

A real maintenance iteration Implemented

A GitHub Actions warning identified a deprecated runtime in the checkout and setup-node actions. Updating those actions to v5 addressed that warning; the site's configured build runtime remained Node.js 22.

The lesson: maintain the pipeline as well as the application, and distinguish a deprecation warning from a deployment failure.

05 / Operate & evolve

Know what can fail.
Know when to change.

Managed hosting reduces server work; it does not remove operational responsibility. The next improvements should follow observed risk and product demand.

Bad release or failed deployment Planned hardening

Today: build and source checks run before upload. Git records the changes, but a successful upload alone does not prove the live experience works.

Next: add post-deployment route checks, define rollback to a known-good revision, and document a recovery exercise.

Trigger: before introducing a higher-impact workflow or increasing release frequency.

Cost, traffic, and availability Planned monitoring

Today: the selected Free tier fits the small static workload. Domain renewal is separate; no measured traffic or uptime claim is made here.

Next: review usage against published limits, monitor public-route availability, and evaluate a paid plan when usage or reliability requirements demand it.

Tradeoff: monitoring and higher hosting tiers add expense, so set the requirement before buying the service.

DNS, certificates, and dependencies Planned safeguards

Today: Azure manages the site's HTTPS certificate; the repository installs dependencies from its lockfile.

Next: add domain-renewal reminders, certificate-expiry checks, dependency alerts, and dedicated secret scanning. Document token rotation.

Trigger: routine maintenance, provider notices, or an identified vulnerability.

A growing knowledge library Demand-led

Today: a static index is enough for two articles and a manual review process.

Next: add categories when navigation becomes difficult, then a static search tool such as Pagefind. Consider an opt-in publication helper only when repeated copying becomes costly.

Boundary: never replace selective approval with whole-vault publishing.

More interactive product requirements Demand-led

Today: no accounts, private state, comments, or application API.

Next: use an isolated interactive component for a browser-only tool. Evaluate an API and database only when a feature genuinely requires server-side or private persistent state.

Decision rule: evolve the current architecture before considering a framework rewrite.

What I would improve next

Make recovery as deliberate as deployment.

My next engineering priorities are a documented rollback path, automated pull-request checks, and a lightweight live-site health check. A larger architecture can wait.

The most valuable outcome was not adding more technology. It was learning which responsibilities the product actually needed me to own.
